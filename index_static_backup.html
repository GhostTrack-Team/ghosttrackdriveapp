Starting point

Over 10 million heavy commercial vehicles operate on Indian roads with almost no blind-spot protection. Existing systems — proximity sensors, basic cameras — either lack intelligence or cost too much for fleet operators to adopt. With AIS-186 approaching, the timing created a real window to build something that could actually help.

We didn't start with a solution. We started with a concept document, three people with basic Python knowledge, no trained model, no dataset, no working hardware, and no certainty about which components we'd even be given. Everything below is what happened between that starting point and a working system.

The build, as it actually happened

Not a plan executed cleanly — a sequence of mismatches, fixes, and rebuilds, each one forcing a deeper understanding of the system than working code on the first try ever would have.

01
Component mismatch

Plan vs. reality

The concept called for 24GHz mmWave radar and LRA haptics on an ESP32-S3. What we were actually issued was an ultrasonic sensor and standard servos — cheaper, easier to source, and fundamentally limited: ultrasonic loses reliability above 30km/h and in rain, servos are too bulky for a steering wheel.

Rather than wait, we wrote two firmware versions in parallel — v1 for what we had, v2 for the spec we wanted — and made the case to our HOD for the real components. A ₹2,000 grant followed.

Ultrasonic + servo→Dual Waveshare S3KM1110 mmWave radar
02
Hardware ≠ datasheet

The board wasn't what the datasheet promised

Firmware v2 assumed ESP32-S3 GPIO mapping. Wired up, the radar stayed silent. After checking code and baud rates, the fault turned out to be a split breadboard power rail — the two halves weren't electrically connected. Confirmed rail by rail with a multimeter.

Fixing that exposed a second problem: GPIO 16/17 existed on the datasheet but not on the physical header. We remapped, kept building, and once real hardware arrived, retargeted properly — radar and Pi link on two independent UART channels feeding one fusion layer.

GPIO 16/17→GPIO 21/22 (radar) · GPIO 26/27 (Pi link)
03
Dataset

From 46 images to 8,570

Early modelling was split across three disconnected Colab notebooks with mismatched class names. We scrapped all three and rebuilt into one unified pipeline. The first real training run used a Kaggle set with only 46 usable images — nowhere near enough.

We rebuilt the dataset from COCO 2017, Roboflow Indian-road sets, and the original Kaggle images: 8,570 images across 10 classes. Along the way: expired API keys, GPU quota resets, and one disconnect that cost a 3–5 hour run outright.

46 images, 3 notebooks→8,570 images, 1 pipeline
04
Detection quality

Why one model wasn't enough

With YOLOv8n trained (100 epochs, mAP@0.5 = 0.689), testing on real road images showed the gap that mattered most: the model was missing persons, motorcycles, and bicycles — the exact road users GhostTrack exists to protect. COCO's person imagery is front-facing and Western-context; a truck-mounted side camera sees people from a completely different angle.

Instead of more training cycles, we adopted a dual-model architecture: pretrained COCO YOLOv8n for people/cyclists (83–87% confidence), our custom model for India-specific classes — auto-rickshaw (91.6%), tractor (90.6%), e-rickshaw, LCVs.

05
Three camera generations

Chasing the right eye

Gen 1 — USB webcam: worked in Colab, poor low-light, no wide-angle coverage.

Gen 2 — 160° fisheye USB: better field of view, but USB bandwidth bottlenecked frame rate once real-time inference ran on the Pi.

Gen 3 — Raspberry Pi Camera Module (OV5647, CSI): a full rewrite from cv2.VideoCapture() to Picamera2, bypassing USB entirely.

The hardware kept evolving: Pi 4 to Pi 5 with dual CSI cameras needed explicit dtoverlay entries to enumerate reliably. VNC rendering with cv2.imshow() was unreliable, so we switched to a Flask MJPEG stream. Sustained inference pushed the Pi past 85°C — solved with active cooling.

USB webcam→Dual CSI · Picamera2 · Flask MJPEG
06
Haptics

From pointing servos to felt vibration

The original concept used two PCA9685-driven servos that physically pointed toward danger. It worked, but servos are large, current-hungry, and impractical to embed inside a steering wheel rim.

We pivoted to 10mm ERM coin motors (under 2g), driven through BC547 transistors on the ESP32's PWM peripheral, embedded at the 9 and 3 o'clock positions of a custom 3D-printed wheel. Two intensities: CRITICAL as continuous full power, AWARENESS as a pulsed partial pattern — felt in the hand closest to the threat, not seen or heard.

Servo + PCA9685→Coin motor + BC547 + LEDC PWM
07
Fusion logic

Getting the alert logic right

The first version was radar-only: anything closer than a fixed threshold triggered a warning — walls, parked vehicles, and speed bumps all set off false alarms. A system that cries wolf isn't trustworthy in a cab.

We rebuilt it in stages: AND logic (radar proximity + vision-confirmed vulnerable road user), a three-state machine (SAFE / AWARENESS / CRITICAL), speed-adaptive thresholds (~1.5m city vs. 5.0m highway), a simulation mode for indoor testing, and a WiFi SoftAP dashboard so the system can be checked from a phone with no internet.

08
Two computers, one link

Making the Pi and the ESP32 talk

The Pi 5 runs Linux and Python; the ESP32-S3 runs bare-metal C++. We defined a UART protocol from scratch — the Pi sends plain-text strings like LEFT:person, RIGHT:bicycle, or CLEAR, parsed by the ESP32 as one input into fusion.

Getting the link up meant mapping Pi UART GPIOs correctly, enabling hardware UART, and confirming /dev/ttyAMA0. On the radar side, the initial ASCII parser didn't work at all — the S3KM1110 transmits structured binary frames, so we built a proper state-machine binary parser instead.

09
Physical form

Building something you can actually show someone

Rather than demo on a bare breadboard, we designed and 3D-printed a 33×10×12cm scale model of an Indian HCV — seven printed pieces, dovetail joints, internal chassis wire channels, camera mounts at front-left and front-right. Every wire is routed internally except the four coin-motor leads, which exit through the chassis floor by design.

A working circuit on a table is a prototype. A scaled truck with cameras mounted where they'd actually sit is a use case anyone understands at a glance.

System status · live at time of writing

Where things stand now

Software, dataset, and firmware are complete independently on both boards. What's left is physically connecting them.
